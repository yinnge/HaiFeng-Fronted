## ★ 调研推翻的两个预设（DB 实测）
1. **`t_industry_detail` 的 8 个 JSONB 90/90 全是 `{}`**，`short_description` / `detailed_description` 也 90/90 为空，`talent_gap` 同样全空。详情接口真正有值的只有主表 9 个概览指标（市场规模 / 年增长率 / 投资热度 / 四大趋势）。旧详情页那 8 个「深度数据」Tab 点开全空白 → 决定「以真实指标为主体 + 空 Tab 不摆」。
2. **后端 `IndustryDetailVO` 不含 `id` / `category` / `description`**（前端 `types/industry/index.ts` 里 `category?: string` 是永远拿不到的幽灵字段）。行业简介长文本 `description` 90/90 有值，但只在 `IndustryListVO`。→ 并发补一次 `GET /industry/list?ids=<id>` 拿 `description` + `category`，失败静默降级。
3. 其它：`/industry/{id}/detail` 仅 `@RequireLogin`；`/industry/enterprises` 是 `@RequireVip` 且 `t_enterprise_industry` **0 行**（VIP 也返回空）；`IndustryListVO.id`（Long）缺 `@JsonSerialize`，但前端 `request.ts` 已用 `json-bigint(storeAsString)` 兜住，本平台不丢精度。

## ★ 经验
- **「详情 VO 有什么」必须逐字段读 Java 源文件**，不能信前端 types：本页 types 里那个 `category?: string` 是后端根本不返回的幽灵字段，靠它做门类标签和深链会静默失效。
- **DB 全空时不要按设计意图搭骨架**：8 个 JSONB 的 key 名单只能从 admin 导入代码推断、无任何真实样本，写死专用组件等于赌字段名；通用「按值类型渲染」既更省代码又零风险。
- 重构前先跑一次 `git diff` 看有没有并行任务遗留的未提交改动：本次 `.workbuddy/memory/2026-11-12.md` 有上一轮行业列表页日志未提交，提交时用精确路径 `git add`，绝不 `git add -A`。
