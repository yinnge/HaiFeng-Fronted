## 公务员（及全部 admin）状态切换失败：CORS 缺 PATCH
- 现象：公务员操作栏点"报名中/已结束/即将开始" → 前端"操作失败"，后端日志只有 `Securing OPTIONS /.../status`，无后续 PATCH。

## 全就业模块删除改造：软删除失效根因 + 改为"禁用=软删除、删除=物理删除"
- 现象：备考指南点"硬删除"提示成功但数据还在。后端日志实证：UPDATE 语句**没有 is_deleted 字段**。
- 根因：`application-dev/prod.yml` 全局配置 `logic-delete-field: isDeleted`（MyBatis-Plus 逻辑删除）。该配置下 **updateById 会自动排除逻辑删除字段**（防止业务误改删除状态）→ 所有 `setIsDeleted(true) + updateById` 写法全部失效。selectById/selectPage 会自动带 `is_deleted=false` 条件。
- 影响面：**12 个就业模块 ServiceImpl 的 delete() 全部失效**（civil/institution/military/selection/teacher/healthcare/finance/community/welfare/grassroots/notice/guide）；guide/notice 的 updateStatus（禁用）也失效。batchDelete 用 `Wrappers.lambdaUpdate().set(isDeleted,true)` 是有效的（wrapper 不受排除影响）。
- 用户确认的方案：**删除=物理删除（单条+批量），禁用=软删除**。
- 后端改动（24 文件，**需重启 haifeng-admin 生效**）：
  - 12 个 Mapper（common）加 `physicalDeleteById`（`@Delete("DELETE FROM t_xxx WHERE id=#{id}")`）+ `physicalDeleteBatchIds`（`<script>` foreach IN）——自定义 @Delete SQL 不被逻辑删除拦截器转换，是纯物理删除。表名：t_civil_position/t_institution_position/t_military_position/t_selection_position/t_teacher_position/t_healthcare_position/t_finance_position/t_community_position/t_public_welfare_position/t_grassroots_project_position/t_notice/t_exam_guide。
  - 12 个 ServiceImpl 的 delete/batchDelete 改调物理删除方法。
  - guide/notice 的 updateStatus 改为 `update(null, Wrappers.lambdaUpdate(X.class).set(isDeleted, status==0).eq(id))`（wrapper 显式 set，绕开 updateById 排除）——禁用/隐藏生效。
- 前端：GuideTable "硬删除"→"删除"、"批量硬删除"→"批量删除"；guide 禁用确认文案病句修复。其他 11 模块按钮文案本就是"删除"。删除确认文案"永久删除/不可恢复"在物理删除下变为准确，保留。
- 验证：前端 typecheck 51 错误（存量不变）；后端 grep 无 `setIsDeleted(true)` 残留、12 Mapper 方法齐全。Java 未编译（无 maven）。
- 教训：**全局逻辑删除配置下，改 is_deleted 一律用 `update(wrapper.set(isDeleted,...))` 或 `deleteById`，绝不能 `setIsDeleted+updateById`**；真物理删除需自定义 @Delete SQL。

## 备考指南/公告：启用报 404 修复（连带 detail/delete/update 同类隐患）
- 现象：禁用正常、启用报"备考指南不存在"（404）。日志实证：updateStatus 里 `selectById` 生成的 SQL 带 `AND is_deleted=false`，**禁用记录（is_deleted=true）查不到 → 返回 null → 404**。

- 修复（guide/notice 两模块，8 个 ServiceImpl 方法 + 2 个 Mapper 各加 selectXxxById 自定义查询）：
  - `updateStatus`：去掉 selectById，直接 `update(null, wrapper.set(isDeleted, status==0).eq(id))` + 检查影响行数（updated==0 才抛 404）。
  - `detail` / `update`：selectById → **自定义 XML 查询 `selectGuideById`/`selectNoticeById`**（SELECT ... WHERE id=?，不带 is_deleted 条件，忽略逻辑删除过滤）。
  - `delete`（物理删除）：去掉 selectById 前置检查，直接 `physicalDeleteById(id)` + 检查返回值（deleted==0 才抛 404）——禁用记录也可物理删除。
- 经验教训：**凡是要操作"可能已禁用（is_deleted=true）"的记录，都不能用 MP 内置 selectById 校验存在性**（它自动带 is_deleted=false）；要么用自定义 SQL 查询，要么用 update/delete 的返回影响行数判断。此模式适用于将来其他模块做"查禁用/状态切换"。

## 备考指南/公告：启用仍 404 —— update(wrapper) 也被逻辑删除注入，必须自定义 @Update
- 现象：启用被禁用的公告仍报"公告不存在"。日志实证：`UPDATE t_notice SET is_deleted=? WHERE is_deleted=false AND (id = ?)` **Updates: 0**。
- 根因（修正上一轮误判）：**MP 的 `update(entity/wrapper)` 同样会自动注入 `WHERE is_deleted=false`**（不只是 selectById/updateById）。对已禁用记录（is_deleted=true）条件不匹配 → 0 行 → "0 行抛 404"误报。上一轮以为 update(wrapper) 不受注入（依据 batchDelete"正常"）是错的——batchDelete 只是操作对象都是启用记录才碰巧正常。
- 修复（guide/notice，6 文件）：
  - Mapper 加 **`updateIsDeleted` 自定义 @Update**（`UPDATE t_xxx SET is_deleted=#{isDeleted} WHERE id=#{id}`，无任何逻辑删除条件）→ updateStatus 改调它，0 行才 404。
  - **update()（修改）换 XML 动态 update**（`updateGuide`/`updateNotice`：`UPDATE t_xxx <set><if>字段</if> updated_at=now()</set> WHERE id=#{id}`）——原 updateById 同样注入 WHERE is_deleted=false → 禁用记录"静默不更新"。tags 数组列占位符要带 typeHandler。
- 终版结论（guide/notice 全部操作禁用记录的方法）：查询用自定义 XML select（selectXxxById/selectXxxPage）、状态切换用 @Update 直写、修改用 XML 动态 update、物理删除用 @Delete——**凡是碰 is_deleted 或可能已禁用的记录，一律自定义 SQL**。
